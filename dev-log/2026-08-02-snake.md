## Work Completed

### `IComponent` now derives from `Core::IUpdatable`, making `Update(float)` mandatory

`core/components/i-component.hpp` changed from a bare virtual destructor to
`class IComponent : public Core::IUpdatable`, pulling in the pre-existing
`Core::IUpdatable::Update(float) = 0` pure virtual (`core/life-cycle-hooks/i-updatable.hpp`).
This is a stricter contract than the design doc originally proposed — the doc called for a
**non-pure** `virtual void OnUpdate(float) {}` so existing components wouldn't need touching.
Going pure instead meant every existing concrete component needed a real override:
`TransformComponent2D`, `ColliderComponent2D`, `RenderComponent2D`, `InputComponent`, and
`SnakeBodyComponent` all gained an empty `Update(const float) {}` stub this commit.

### Components are ticked by walking registrars, not by `Entity::Update()` iterating its own map

The design doc's plan was for `Entity::Update()` to iterate its own `components` map and call
`OnUpdate` on each. What actually got built is different: `IEntityComponentPipeline` now
derives from `Core::IOnUpdatable` (`OnUpdate(float) = 0`), and `EntityComponentPipeline` owns
both a `ComponentDispatcher` and a new `ComponentUpdater`, sharing the same
`Core::Entities::EntityComponentRegistrars` vector between them. `ComponentUpdater::Run`
(`component-updater.cpp`) walks every registrar and calls `GetComponentsFromRegistry()` on
each, then calls `Update(deltaTime)` on every returned component. `EntityManager::OnUpdate`
calls `this->componentPipeline.OnUpdate(deltaTime)` to trigger this each frame. Net effect —
components tick — is the same as the design doc's goal, but the mechanism is registrar-driven
aggregation rather than per-entity map iteration. See **Architectural Decisions** below.

### Registrars now own their components and expose them uniformly

`IComponentRegistrar` gained `GetComponentsFromRegistry()`, implemented by all three concrete
registrars:

- **New** `GameComponentRegistrar` (`registrars/game-component-registrar.{hpp,cpp}`) —
  registers anything deriving from the new `Engine::Components::GameComponent`, owning each
  via `std::vector<std::unique_ptr<GameComponent>>`.
- `InputComponentRegistrar` and `RenderComponentRegistrar` were retrofitted with the same
  `std::vector<std::unique_ptr<T>>` ownership pattern and a matching
  `GetComponentsFromRegistry()` that returns raw `IComponent*` pointers.

`ComponentDispatcher` changed from owning its own `vector<unique_ptr<IComponentRegistrar>>`
and exposing `AddRegistrar()` to taking a `EntityComponentRegistrars&` by reference in its
constructor — `EntityComponentPipeline` is now the actual owner of the registrar list, and
hands the same reference to both `ComponentDispatcher` and the new `ComponentUpdater` so they
operate on one shared collection instead of each keeping their own.

### New component base classes: `Engine::Components::Component` and `GameComponent`

`engine/components/component.hpp` (implements `IComponent::Update` as a no-op) and
`engine/components/game-component.hpp` (extends `Component`, also a no-op override) are new.
`SnakeBodyComponent` was switched from directly implementing `Core::Components::IComponent` to
extending `Engine::Components::GameComponent`, making it the first (and so far only) consumer
of the new `GameComponentRegistrar` — this is scaffolding for `MovementComponent`
(`UE-0058`), which is expected to be a `GameComponent` too, not yet built this commit.

### `CMakeLists.txt` picked up the two new source files

`src/engine/entities/component-updater.cpp` and
`src/engine/entities/registrars/game-component-registrar.cpp` were added to the explicit
`add_executable(...)` list.

### Housekeeping

`RenderComponent2DManager`'s namespace nesting was flattened from nested `namespace Core {
namespace Rendering { ... } }` to chained `namespace Core::Rendering { ... }` blocks, and its
trailing `};` typo (extra semicolon after a namespace closing brace) was fixed to `}`. Debug

## Lessons Learned

### Pure vs. non-pure interface hooks change the size of a "just add a hook" change

The design doc explicitly chose a non-pure `virtual void OnUpdate(float) {}` for
`IComponent` specifically so existing components wouldn't need edits. What was actually
built — `IComponent : public Core::IUpdatable`, whose `Update(float)` is pure — meant the
"add one hook" step touched five existing files (`TransformComponent2D`,
`ColliderComponent2D`, `RenderComponent2D`, `InputComponent`, `SnakeBodyComponent`) purely to
satisfy the vtable, all with identical empty-body overrides. Worth keeping in mind for
`UE-0057`'s eventual write-up: functionally the goal ("components can tick") was met, but at
a larger edit surface than the doc planned for.

### Reusing an existing generic interface (`IUpdatable`/`IOnUpdatable`) versus writing a
component-specific one

Both `Core::IUpdatable` (`Update(float)`) and `Core::IOnUpdatable` (`OnUpdate(float)`) already
existed in `core/life-cycle-hooks/` before this session, used elsewhere in the engine's
`Entity`/`System` hierarchy. This commit reused both rather than declaring new
component-specific virtuals — `IComponent` picked up `IUpdatable`, `IEntityComponentPipeline`
picked up `IOnUpdatable`. Keeps the naming consistent with how the rest of the engine already
expresses "this thing ticks" vs. "this thing dispatches a tick downward."

## Architectural Decisions

### Component ticking is registrar-driven aggregation, not `Entity` iterating its own component map

The design doc proposed `Entity::Update()` walking its own `components` map and calling
`OnUpdate` on each — the simplest possible version, entirely local to `Entity`. What got built
instead routes through the existing registrar system: `EntityComponentPipeline` owns the
shared `EntityComponentRegistrars` list, `ComponentDispatcher` populates it as components are
registered/unregistered per entity, and the new `ComponentUpdater` walks *all* registrars
(across *all* entities) once per call and ticks every component it finds. This reuses the
registrar abstraction that already existed for render/input registration instead of adding a
second, independent iteration path on `Entity` itself. Trade-off worth flagging explicitly:
component ticking is no longer scoped per-entity the way `Entity::Update()` would have made
it — it's a flat sweep over every registered component in the scene, which is where the
`UE-0064` correctness question below comes from.

### `GameComponent` introduced as an intermediate base, ahead of `MovementComponent` actually
existing

Rather than build `MovementComponent` directly against `IComponent`, this commit first
introduced `Engine::Components::Component` and `Engine::Components::GameComponent` as a
two-tier base (`Component` = generic engine-level default-update component;
`GameComponent` = the tier game code is expected to extend) plus a dedicated
`GameComponentRegistrar`, and migrated `SnakeBodyComponent` onto it as the first real user.
This front-loads the "give game components their own registrar/category, separate from
render/input" decision before `MovementComponent` itself needs it, rather than retrofitting
it once `MovementComponent` lands.

### Follow-up (post-commit discussion): component ticking moves to entity-scoped iteration; registrars stay as a typed index, not the update mechanism

Talked through `UE-0064` after the fact. The registrar-driven sweep loses entity active-state
gating for free — `Entity::Update()` (and everything the doc's original per-entity-map
approach would have inherited) only fires for active entities; the registrar sweep in
`ComponentUpdater::Run` has no notion of "active" at all and ticks every registered
component regardless of its owner's state, which is also the root cause of `UE-0064`'s
double-counting (nothing scopes the sweep to "once per frame" once it's decoupled from a
specific entity).

Decided direction: pass the `IEntity*` into `ComponentUpdater` and have it walk that single
entity's own components, the same way `ComponentDispatcher::Dispatch`/`Teardown` already
operate per-entity — so ticking becomes naturally scoped and active-gated again, matching
what the design doc intended.

The typed-registry idea (each registrar owning `vector<unique_ptr<T>>` and exposing
`GetComponentsFromRegistry()`) isn't wasted by this — it still has real upsides independent
of ticking: category-wide queries without walking the entity list (e.g. "every
`RenderComponent2D` in the scene," which the render manager already needs; "every currently
bound `InputComponent`" for a debug overlay), and ownership that lines up naturally with the
`Register`/`Unregister` lifecycle the registrar already drives. Plan is to keep the
registries for that purpose and have `ComponentUpdater` stop reading from them — it becomes a
lookup table other things can query, not the update mechanism itself.

## Known Issues Carried Forward

- [ ] **UE-0064** — NEW, correctness bug: `EntityManager::OnUpdate` (`entity-manager.cpp`)
  calls `this->componentPipeline.OnUpdate(deltaTime)` **inside** the `for (auto& object :
  this->entities)` loop, rather than once per frame outside it. Since `ComponentUpdater::Run`
  already sweeps every registered component across every registrar (not just the current
  entity's own components — see the registrar-driven design above), this means every
  component in the scene gets `Update(deltaTime)` called once per *entity currently in
  `EntityManager`*, not once per frame. With N entities alive, every component ticks N times
  a frame instead of once. Currently invisible because all `Update()` overrides added this
  commit are empty stubs — will start mattering the moment `MovementComponent::Update`
  actually does something (e.g. accumulating `moveTimer`), where it would make the snake
  appear to move at N× speed. It also ticks components on *inactive* entities, since the
  sweep has no notion of `IsActive()` at all. Decided fix (see Architectural Decisions,
  "Follow-up"): pass the `IEntity*` into `ComponentUpdater` and have it iterate that entity's
  own components, the same way `ComponentDispatcher` already does per-entity — restores
  active-state gating and natural once-per-frame scoping in one move. Registrars keep their
  typed `vector<unique_ptr<T>>` registries as a separate lookup/query mechanism (category-wide
  queries like "every `RenderComponent2D` in the scene"); `ComponentUpdater` just stops
  reading from them.
