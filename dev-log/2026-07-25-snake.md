### Two `Core::Zip` crashes from a shared root cause, fixed one at a time

Added `ZeroValueFor(ActionValueType)` to `core/input/action-value.hpp` — a `switch` over
`Boolean`/`Axis1D`/`Axis2D` returning a correctly-typed zero `ActionValue`. This exists because
`ActionValue` is `std::variant<bool, float, Vector2D>`, and a bare default-constructed
`ActionValue{}` always value-initializes to the *first* alternative (`bool`), regardless of what
type the action actually is. Two call sites were doing exactly that and both hit
`Core::Zip`'s `assert(a.index() == b.index())`:

1. `KeyboardInputSource::GetActionValue`'s `std::accumulate` seed — crashed the moment any
   `Axis1D`/`Axis2D`-typed key (i.e. any movement key) was pressed, since the fold's `bool` seed
   got `Accumulate`d against a real `float` contribution. Fixed by seeding with
   `ZeroValueFor(action.type)` instead of `ActionValue{}`.
2. `ActionRouter::BindAxis`'s `AxisBinding::lastValue` initial value — crashed *instantly on frame
   one*, before any key press, because `ActionRouter::Update()`'s first `Distance(current,
   lastValue)` call compared a freshly-polled `float`/`Vector2D` against the still-`bool`
   `lastValue`. Fixed the same way, seeding via `ZeroValueFor(this->actions.Get(name).type)`.

The user's own first attempt at `ZeroValueFor` didn't compile — it copy-pasted `ValueTypeOf`'s
`std::visit` body without adapting the parameter, but `ZeroValueFor` takes an `ActionValueType`
enum, not a real `std::variant`, and there's no `std::visit` overload for a plain enum. Confirmed
by an actual compile attempt, not just inspection. Second pass switched on the enum directly, which
compiles and is the version that shipped.

### Window double-free/segfault on clean exit, fixed across two false starts

`RaylibWindowFacade` now has a `closed` guard bool, checked in both the destructor and
`CloseWindow()`. Root cause: `Application::Shutdown()` explicitly called `window->CloseWindow()`,
and then `~RaylibWindowFacade()` called raylib's `::CloseWindow()` again during static teardown —
raylib's `CloseWindow()` isn't idempotent, so the second call freed already-freed internal
texture/shader/font state. Two attempts before this was actually fixed:

1. First pass guarded only the destructor — left the *public* `CloseWindow()` method (the one
   `Shutdown()` actually calls) still capable of firing unconditionally, so the double-free
   persisted, just with a different heap-corruption signature (`double free or corruption
   (!prev)` instead of `tcache 2`) because the crash now happened via a different call path.
2. Second pass added the guard to `CloseWindow()` too, but its body called the unqualified
   `CloseWindow()` — which resolved to itself (the member function), not raylib's `::CloseWindow()`
   — causing infinite recursion and a stack-overflow segfault instead. Diagnosed from the absence
   of raylib's own "TEXTURE unloaded / Window closed successfully" log lines, which confirmed
   raylib's real teardown was never reached at all.
3. Final version qualifies the real call as `::CloseWindow()`, with the guard set once, shared by
   both the destructor and the public method.

## Lessons Learned

### `std::variant`'s Default Constructor Always Picks the First Alternative

Both `Core::Zip` crashes this session trace back to the same C++ fact: a default-constructed
`std::variant<bool, float, Vector2D>` is never "empty" or "unset" — it's always alternative `0`
(`bool`, value `false`). Any code path that seeds/defaults an `ActionValue` with a bare `{}` is
implicitly claiming "this is a boolean" whether or not that's true, and the mismatch only surfaces
the moment it's compared or combined against a real value of a different alternative. Worth
remembering as a variant-specific trap distinct from, say, `std::optional`, which does have a
genuine empty state.

### An Unqualified Call Inside a Member Function of the Same Name Resolves to Itself, Not the Global

`RaylibWindowFacade::CloseWindow()`'s infinite-recursion bug was caused by writing `CloseWindow();`
inside the member function body — unqualified name lookup finds the enclosing class's own method
before it ever considers the global `::CloseWindow()`, even though the intent was obviously to call
raylib's function. This is a general C++ shadowing trap whenever a facade/wrapper method shares its
name with the underlying library call it's wrapping — the `::` qualifier isn't optional style, it's
load-bearing the moment names collide like this.

### Diagnosing "No Log Output" Is as Informative as Diagnosing a Stack Trace

The infinite-recursion segfault produced no application-level crash message and, critically, none
of raylib's own teardown log lines ("TEXTURE unloaded", "Window closed successfully") — which was
itself the diagnostic signal that raylib's real `::CloseWindow()` was never reached at all, pointing
straight at the self-referential call rather than needing a debugger/backtrace to find it.

### Movement-Tick / Input-Sampling Coupling, and Why It Matters for Perceived Responsiveness

A design discussion mid-session (prompted by "A/D feel extremely unresponsive") traced actual
input latency through the whole pipeline — `ActionRouter`'s threshold/`Distance` change-detection
(default `0.01f`, cleared instantly by any real key-down) and 60fps polling were both ruled out as
non-issues by direct inspection of `Distance()`'s implementation and `WindowConfig::targetFPS`. The
real cause was `Snake::Update()` calling `SetDirection()` every frame rather than once per movement
tick (`speed = size * 5.0f` ⇒ a 200ms tick interval) — direction changes registered instantly in the
input system but were only visible once per tick, and a same-tick reversal could get silently
overwritten by a later frame's read before the tick ever consumed it, producing both sluggish feel
and a diagonal-direction glitch when switching axes quickly (the two axis callbacks each only wrote
their own component, so a stale opposite-axis value could linger uncleared). Agreed direction: latch
only the single most-recent commanded direction (a `pendingDirection`-shaped slot, overwrite —
not append — on each keypress), and consume-and-clear it once per tick rather than reading live
state every frame. This is a single latched slot, not a true FIFO queue, since only the most recent
command since the last tick consumption matters.

### Y-Axis Convention: Isolate the Flip at the Rendering Boundary, Not in Gameplay Logic

A separate discussion (wanting `+Y` to mean "up" throughout the engine, more intuitive than
raylib's screen-space `+Y = down`) confirmed there's currently no camera/viewport transform layer
anywhere in the codebase — rendering is 1:1 pixel-for-unit straight into raylib calls. Established
that the correct seam for the flip is the raylib-facade rendering boundary itself
(`RaylibRendererFacade::DrawRectangle`, and equivalently the UI/debug-HUD facades if all screen
elements should honor the convention), not `Snake::Move()`/`SetDirection()` or the key bindings —
which turned out to already be written in the target math convention (`W`/`Up: +1.0f`) and only
*look* inverted today because nothing flips at render time yet. No reverse (screen→engine)
conversion is needed, since this game has no mouse input anywhere.

## Architectural Decisions

### `Entity::OnRegistration()` Centralizes `TransformComponent2D` Construction

Previously every `Entity` subclass (`Entity` itself, `Apple`, `SnakeSegment`) independently
hand-rolled a `make_unique<TransformComponent2D>(...)` call in its own constructor or
`OnRegistration`. Moved this into a single `Entity::OnRegistration()` that adds the component
through the existing component-registration system and caches a raw `transform` pointer for
subclasses to use — subclasses now call `Entity::OnRegistration()` first and build on top, rather
than each re-deriving the same construction logic. `IEntity::GetTransformComponent()` was removed
from the interface entirely in favor of this cached member, since nothing outside the entity itself
needs polymorphic access to it once it's a plain cached pointer.

### Movement State and Logic Move From Central `Snake` to Per-`SnakeSegment`

Per the session's own plan ("Snake should be flattened into SnakeSegment and SnakeHead"),
`accumulatedDistance`/`speed`/`size`/`direction` and the `Update()`/`Move()`/`SetDirection()`
methods that used to live solely on `Snake`, orchestrating every segment's position from one place,
moved down onto `SnakeSegment` itself — each segment now owns and advances its own movement state.
This is a deliberate decentralization, not yet fully realized in the shipped commit (`Snake`'s own
versions of these methods are commented out mid-migration, not deleted) — see Known Issues for the
concrete finishing work.

### `pendingDirection`: a Single Latched Slot, Not a FIFO Queue

Decided (see Lessons Learned) that the fix for movement-tick/input coupling should latch only the
single most recently commanded direction — last-write-wins — rather than a true multi-entry queue
that processes every intermediate command in order. Since only the freshest input at tick-consumption
time matters for this game, a `Vector2D` slot that gets overwritten on each axis-change callback is
sufficient and avoids unnecessary queue/liveness bookkeeping. `SnakeHead::pendingDirection` exists
in the shipped code as the starting point for this, declared but not yet read or written anywhere.
