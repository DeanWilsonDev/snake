## Work Completed

### Input Pipeline (per the design doc)

Landed close to the doc's proposal: `Core::Input::IInputSource` (level-state-only,
`IsActionDown`), `Core::Input::IInputDispatcher` (`AddSource` + `Run`, extending the new
`Core::Systems::IDispatcher`), and `Engine::Input::InputDispatcher` as the concrete
aggregator — OR-ing every source's state per `Action`, edge-detecting once centrally, and
publishing `InputActionPressedEvent`/`InputActionReleasedEvent` on transitions.
`Engine::Input::Sources::KeyboardInputSource` is today's `InputSystem::IsActionDown` body,
moved down a layer unchanged. `InputSystem` itself is now the pipeline owner and an
`ISystem` — `OnUpdate` just calls `dispatcher.Run()`.

`Action` moved from `Engine::Input` to `Core::Input` (`core/input/action.hpp`, renamed from
`engine/input/input-action.hpp`) so it's usable from `Core::Input::IInputSource` without a
`Core`→`Engine` dependency inversion. `KeyMap` similarly moved to `core/input/key-map.hpp`.

### `Application` Systems Extension Point

Added `Core::Systems::ISystem` (`IOnUpdatable` + `Debug::IOnDebugable`) and
`IApplication::RegisterSystem`. `Application` now holds
`std::vector<std::shared_ptr<Core::Systems::ISystem>>` and drives every registered system's
`OnUpdate`/`OnDebugUpdate`/`OnDebugRender` once per frame, before the scene manager runs.
`InputSystem` is the first system registered this way (`application.cpp:80-84`); the
`// SIDE QUEST` comment left in `Initialize()` flags `EntityManager`/`sceneManager` as future
candidates for the same treatment.

Two build failures came up wiring this in, both fixed this session:

- **`AddSource`/`RegisterSystem` push_back type mismatches.** `InputDispatcher::AddSource`
  originally did `this->sources.push_back(source)` against a
  `vector<unique_ptr<IInputSource>>` parameter taken by value — `unique_ptr` isn't
  copyable, so this needed `std::move(source)`. Separately, `Application::RegisterSystem`
  pushed a bare `ISystem&` into a `vector<shared_ptr<ISystem>>`; the real fix wasn't a cast
  at the push_back site but changing the interface itself
  (`i-application.hpp`/`application.hpp`) to take/store the `shared_ptr` — passing a raw
  reference derived from an existing `shared_ptr` (`*inputSystem`) would have built a second,
  independent control block around the same object, freeing it out from under the vector's
  entry the moment the local `inputSystem` in `Initialize()` went out of scope.
- **`RegisterSystem` declared `const` while calling a mutating `push_back`.** After fixing
  the type, `push_back` still failed: `RegisterSystem` overrides an interface method declared
  `const` in `IApplication`, so inside the method `this->systems` was a
  `const vector<...>&` — `push_back` isn't a const member function. Fixed by dropping `const`
  from the interface declaration and both overrides, since registering a system is inherently
  a mutation of `Application`'s own state.

### Event Bus: `bad_any_cast` on First Real Dispatch

After the build went clean, pressing `w` in-game crashed with `bad_any_cast`. Root cause:
`IEventBus::Subscribe`'s dispatch lambda (`i-event-bus.hpp:24`, pre-fix) took
`const IEvent& event` and then called `std::any_cast<const TEvent&>(event)` — but `event`
was never a `std::any` in the first place; `IEvent` (`i-event.hpp`) is a plain polymorphic
base with a virtual destructor, nothing more. The call still compiled, because
`std::any`'s converting constructor silently built a **temporary `std::any` from a sliced
copy of `event`, typed as `IEvent`** — and since the static type at that point was `IEvent`,
not the real derived `TEvent`, the wrapped `std::any` always held `typeid(IEvent)`. Every
subsequent `any_cast<const TEvent&>` against it threw, unconditionally, for every event, on
the first frame anything was actually published. `w` (which maps to `MoveUp`) was simply the
first key that ever hit `InputDispatcher::Run()`'s publish path.

Fixed by replacing the `any_cast` with a plain `static_cast<const TEvent&>(event)`
(`i-event-bus.hpp:24`, `event-bus.hpp`/`.cpp`'s `PublishImplementation`/
`SubscribeImplementation` signatures updated to take `const IEvent&` throughout) — safe
because `Subscribe`/`Publish` already key listeners by `typeid(TEvent)`, so whatever concrete
object arrives for a given type-indexed slot is guaranteed to actually be a `TEvent`.
`std::any`/`<any>` is no longer used anywhere in the event bus.

## Lessons Learned

### `std::any_cast` on a Non-`any` Argument Compiles, Because `std::any` Has a Converting Constructor

The `any_cast` bug above is worth remembering as a general C++ trap: `std::any_cast` requires
a `std::any` argument, but if you pass something else that's copyable, the compiler doesn't
reject it — it implicitly constructs a temporary `std::any` from your argument via `std::any`'s
templated converting constructor, using whatever the argument's **static type** is at the call
site. If that static type isn't the concrete/derived type you meant, you get a slice into the
`std::any`, and every `any_cast` against it fails at runtime with no compile-time signal
anything was wrong. A `static_cast`/`dynamic_cast` against an already-concrete reference is a
completely different (and here, more correct) operation than `any_cast`, but the compiler
won't tell you if you've reached for the wrong one — both compile.

### Interface `const` Qualifiers Propagate Constraints Downward Through Overrides

The `RegisterSystem` build error was a reminder that a `const` on a virtual method in a base
interface isn't advisory — it fixes what the override is *allowed* to do, not just how it's
called. `IApplication::RegisterSystem` being declared `const` meant every override's `this`
was a `const Application*`, which made the `systems` member a `const vector<...>&` inside the
method body regardless of what the concrete class's own member declaration looked like. The
fix had to start at the interface, not at the call site.

## Architectural Decisions

### `Application::RegisterSystem` Takes/Stores `shared_ptr`, Not a Raw Reference

Considered leaving `RegisterSystem(ISystem&)` and constructing a `shared_ptr` around the raw
pointer inside the method (`std::shared_ptr<ISystem>(&system)`) to satisfy the
`vector<shared_ptr<ISystem>>` storage type. Rejected: that builds a second, independent
control block around an object that's already owned by a `shared_ptr` at the call site
(`Application::Initialize`'s local `inputSystem`), so the object gets destroyed the moment
the local `shared_ptr` goes out of scope, leaving `Application::systems` holding a dangling
entry. Landed on threading the `shared_ptr` itself through the interface instead, so ownership
is genuinely shared between the local variable and the stored entry.

### `IInputSource` Reports Raw Level State Only; Edge-Detection Lives Once, Centrally

Per the design doc: `IInputSource::IsActionDown` is the entire interface — no per-source
press/release logic. `InputDispatcher::Run()` is the single place edges get detected
(comparing this frame's OR'd state against `lastFrameDown`). Rejected doing edge-detection
per-source (as the old `InputSystem::IsActionPressed` effectively did, relying on raylib's
own per-frame `IsKeyPressed`), since a planned `GamepadInputSource` won't necessarily have the
same per-frame edge primitive available from its backend — better for every source to report
only what's universally available (is this action currently active) and let one shared place
own the transition logic.
