## Work Completed

### Core shape change: `Action`, `KeyMap`, `ActionSet` — landed and compiles

`Action` (`core/input/action.hpp`) is now a plain `struct{ int id; string
name; ActionValueType type; bool isComposite; }` — no enum, no fixed-size
`keycodes` array. `KeyMap` (`core/input/key-map.hpp`) is
`unordered_map<int, vector<KeyBinding>>`, keyed by `id` rather than by
`Action` itself, so no `operator==`/`std::hash` is needed on `Action`
anywhere in the input layer. A new `ActionSet` (`core/input/action-set.{hpp,cpp}`)
provides `RegisterAction(name, type)` (auto-incrementing `id`), `Get(name)`
(asserts on an unregistered name rather than returning a default `Action`),
`All()`, and `BuildKeyMap(vector<ActionBindingBuilder>)`. `ActionSet` lives
on `Engine::Application` (not `SnakeApplication`) so every game gets one for
free; `IApplication::GetInputActions()` is `const`-only on the interface
(`i-application.hpp:47`), with a second, non-virtual, non-const overload
added directly on `Application` (`application.hpp:84-85`) for `Configure()`
to register into — standard const/non-const overloading, not a
const/mutable split on the field itself (`inputActions` stays `private`).

`InputDispatcher`, `InputSystem`, and `KeyboardInputSource` were all updated
to match: `InputDispatcher`'s constructor takes `vector<Action> actions` and
sizes two `vector<bool>` (`lastFrameDown`/`currentDown`) from it instead of
the old `array<bool, Action::Count>`; `Run()`/`IsActionDown()` iterate/scan
that vector instead of casting an index to the old enum;
`KeyboardInputSource::IsActionDown` now does `keyMap.find(action.id)` (not
`operator[]`, since the method is `const`). `Application::Initialize()`
passes `config.engine.input.actions` as a fourth constructor argument
(`application.cpp:80-82`). This chain compiles and is consistent end to end.

Two bugs the previous session's log had flagged as open (UE-0036) are fixed
as part of this rewrite, confirmed directly in `input-dispatcher.cpp`:
`Run()` now publishes `InputActionPressedEvent{action}`/
`InputActionReleasedEvent{action}` with the real transitioning action
(previously default-constructed, always resolving to enumerator `0`), and
`this->lastFrameDown[i] = isDown` is now actually assigned at the end of the
loop (previously never written at all, so every frame looked like a fresh
transition). Flagging both for confirmation rather than closing outright,
per this log's own ticket-lifecycle rule — see Known Issues below.

### `ActionBindingBuilder` — chainable binding authoring, landed

`core/input/action-binding-builder.{hpp,cpp}` implements the
`Bind(name).Axis1D(keys, scale).Axis1D(keys, scale)` / `.Digital(keys)`
chainable builder discussed at length this session, replacing raw
positional/aggregate-init `KeyMap` construction. `ActionSet::BuildKeyMap`
consumes a `vector<ActionBindingBuilder>` and validates each binding's
contribution type against the action's declared `ActionValueType` via an
`assert` (`action-set.cpp:39-44`) before it's a runtime surprise — except see
UE-0039 below, which breaks that validation for exactly the case it exists to
catch. `SnakeApplication::Configure()` was rewritten to use it:
`MoveForward`/`MoveRight` as `Axis1D` actions (opposite-signed key groups —
`W`/`Up`: `+1`, `S`/`Down`: `-1`, etc.), `Confirm`/`Decline` as `Boolean`.

### `ActionValue` / `ActionValueType` — landed with a real bug (UE-0039)

`ActionValue` is `std::variant<bool, float, Vector2D>`
(`core/input/action-value.hpp`), matching the session's decision to use a
variant rather than Unreal's uniform tagged-vector approach (this codebase
has no generic modifier/trigger pipeline that needs uniform storage). The
`ValueTypeOf(ActionValue) -> ActionValueType` helper — needed by
`BuildKeyMap`'s validation, and originally sketched as pseudocode mid-session
before being pointed out as such — has been implemented, but with a
copy-paste bug: its `if constexpr` chain checks `std::is_same_v<T, bool>`
twice (once correctly for the `Boolean` branch, then again — instead of
`float` — for what should be the `Axis1D` branch). See UE-0039.

### `ActionBindings` — declared, not implemented, not wired to anything (UE-0040/0041)

`core/input/action-bindings.hpp` exists with the `Bind`/`BindAxis`/`Update`
shape discussed this session, but diverges from where the design doc landed
and isn't functional yet:

- No `action-bindings.cpp` — every method is declared, none defined. Nothing
  that includes this header and calls a method would link.
- `Bind`/`BindAxis` return `void`, not the move-only RAII `Handle` the
  session's design settled on — the two problems that motivated `Handle`
  (two listeners on one action clobbering each other via
  `unordered_map<int, function>`; a destroyed `Snake` leaving a dangling
  callback behind after `SceneManager::SwitchTo`'s `Transient`-scene
  teardown, `scene-manager.cpp:23-28`) are both still live risks in this
  shape.
- `BindAxis(name, std::function<void()> callback)` doesn't even accept the
  axis value — the callback signature has no way to receive what changed.
- It's never constructed anywhere. `InputSystem` doesn't hold one; nothing in
  `application.cpp` builds one. `Snake` doesn't reference it at all —
  instead `Snake` was wired directly to `IInputSystem`/`ActionSet` (see
  below), which is exactly the ownership the design doc argues against in
  its own §8 ("Snake shouldn't hold ActionSet/IInputSystem directly... that's
  the wrong owner for that job"), written in the same commit.

### `Snake` movement — event subscription removed, replacement doesn't compile (UE-0042/0043/0044)

The old `Subscribe<InputActionPressedEvent>`/`switch(e.action)`/
`SetDirection(...)` block in `Snake`'s constructor was deleted entirely
(`snake.cpp`). In its place, `Snake::Move()` now does:

```cpp
float vertical   = std::get<float>(this->inputSystem->GetActionValue(this->inputActions.Get("MoveVertical")));
float horizontal = std::get<float>(this->inputSystem->GetActionValue(this->inputActions.Get("MoveHorizontal")));
```

Three separate problems here, each independently blocking:

- `inputSystem` is a reference member (`const Core::Input::IInputSystem&
  inputSystem`, `snake.hpp`), not a pointer — `->` isn't valid on a
  reference to a type with no overloaded `operator->`; needs `.`.
- `IInputSystem::GetActionValue` doesn't exist. `i-input-system.hpp` wasn't
  touched this session — it still declares nothing beyond a virtual
  destructor (confirmed by reading the file directly, not just the diff).
  This doesn't compile regardless of the `->`/`.` fix.
- Even once both of those are fixed, the action names don't match:
  `Get("MoveVertical")`/`Get("MoveHorizontal")` are looked up, but
  `SnakeApplication::Configure()` only ever registers `"MoveForward"`/
  `"MoveRight"`. `ActionSet::Get` asserts on an unregistered name
  (`action-set.cpp:26`) — this would abort at runtime in a debug build, or
  return past-the-end/undefined behaviour in a release build with
  assertions compiled out.

And separately from all three: even if `vertical`/`horizontal` resolved to
real values, `Move()` never does anything with them — no assignment to
`this->direction`, no call to `SetDirection`. Between the deleted
subscription and this, nothing currently updates `Snake`'s direction from
input at all. Movement is non-functional in this commit independent of the
compile errors.

### Build: `action-binding-builder.cpp` missing from `CMakeLists.txt`

`action-set.cpp` was added to the executable's source list
(`CMakeLists.txt:47`), but `action-binding-builder.cpp` — which
`action-set.cpp` depends on via `ActionBindingBuilder` — was not. Every

## Lessons Learned

### `if constexpr` Type-Dispatch Chains Don't Warn on a Duplicated Branch Condition

`ValueTypeOf`'s bug (checking `is_same_v<T, bool>` twice instead of `bool`
then `float`) compiles cleanly and produces no warning — the compiler has no
way to know the second branch was supposed to test a different type; from
its point of view, an unreachable-but-well-formed `else if` is not an error.
Worth remembering as a general pattern risk with hand-written `if constexpr`
dispatch over several types: nothing catches "this branch's condition is
identical to an earlier one" short of actually exercising every alternative
in a test.

### `.` vs `->` on a Reference Member Is Silent Until It Isn't

`this->inputSystem->GetActionValue(...)` against a `const IInputSystem&`
member is exactly the kind of typo that's easy to make when copying a
pointer-shaped sketch (several versions of this session's design discussion
used `IInputSystem*`/pointer language interchangeably with reference
language before settling) — the fix is mechanical once spotted, but nothing
about the surrounding code signals which one is correct without checking the
member's actual declared type.

### Confirming Behaviour by Reading the Code Beats Assuming It

Mid-session, a question came up about whether `ActionBindings::Bind`/
`BindAxis` calls happening after `Initialize()` (rather than during
`Configure()`) was safe, given a future `MainMenu` scene might delay `Snake`'s
construction significantly. Rather than reasoning about it abstractly, this
was checked directly against `SceneManager::SwitchTo`/`ResolveScene`
(`scene-manager.cpp:17-36`, `102-116`), confirming scene construction is
synchronous with no pending/deferred-switch mechanism anywhere in
`SceneManager`. That direct read also surfaced the actual, separate hazard
worth caring about — `Transient` scene teardown (`entry.instance.reset()`)
destroying `Snake` while it may still be registered in `ActionBindings` —
which motivated the `Handle`/RAII design in the doc, not yet in the code (see
UE-0041).

## Architectural Decisions

### `KeyMap` Keys on `int id`, Not `Action` Itself

Considered giving `Action` `operator==`/`std::hash` so `KeyMap` could be
`unordered_map<Action, ...>` directly. Rejected — `Action` already carries a
stable `id` for exactly this purpose, and keying on the plain `int` avoids
adding identity/hashing machinery to a type that's otherwise just a
value-carrying struct. The `int` is also what stays cheap to compare in
`InputDispatcher::Run()`'s per-frame hot path.

### `ActionSet` Lives on `Application`, Not `SnakeApplication`

`ActionSet::Get(name)` is only useful if the instance it was registered on
outlives `Configure()` — a game entity constructed later (e.g. `Snake`)
needs something to still look names up on. Landed on making `ActionSet` a
member of the engine-level `Application` base rather than any one game's
subclass, so every game gets the mechanism without re-deriving it, with a
`const`-only accessor on the public `IApplication` interface (read-only for
anything holding the interface) and a second non-virtual non-const overload
on the concrete `Application` class for subclasses' `Configure()` to
register into.

### `ActionBindings` Should Own `Bind`/`BindAxis` via a Move-Only `Handle`, Not `void`

Decided (documented in the design doc) but not yet applied in the committed
`action-bindings.hpp`: registration should return an RAII `Handle` that
unregisters on destruction, and storage should move from
"one-callback-per-action-id" to a flat list keyed by a unique per-registration
id. Two problems drove this: multiple listeners on the same action
clobbering each other under the current `unordered_map<int, function>`
shape, and a destroyed `Snake` leaving a dangling callback behind once any
scene other than `Gameplay` exists and `Transient` teardown runs. Next
session's implementation of `ActionBindings` should use this shape rather
than the simpler one currently declared.

### `ActionValue` as `std::variant`, Not Unreal's Uniform Tagged Vector

Confirmed this session, applied in the actual code
(`action-value.hpp:11`). Unreal always stores an action's value as a 3-float
vector plus a type tag, because its modifier/trigger pipeline needs to
process any action's value generically as raw float components. This
codebase has no equivalent generic pipeline — each consumer expects one
specific shape — so `std::variant`'s compile-time-checked `std::get<T>`
access was chosen over a type that can be silently misread at runtime.
