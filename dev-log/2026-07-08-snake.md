## Work Completed

### Stage 1 — `EntityManager` Sole Ownership

`EntityManager` changed from a non-owning `std::vector<IEntity*>` to an owning
`std::vector<std::unique_ptr<IEntity>>`. `AddEntity` now takes `std::unique_ptr<IEntity>` by
value and returns a raw observer handle; `RemoveEntity` was implemented (previously declared,
never defined). Verified by full rebuild after fixing one stale caller left over from the
`Snake::body` type change: `gameplay-state.cpp:83` was still calling `.get()` on what is now a
raw `SnakeSegment*`.

### Stage 2 — `Snake` Becomes an Observer

`Snake::body` changed from `std::deque<std::unique_ptr<SnakeSegment>>` to
`std::deque<SnakeSegment*>`. All segment creation now funnels through a single new
`Snake::CreateSegment`, which calls `entityManager.AddEntity(...)` and stores the returned raw
handle — `CreateBody` and `CheckIfShouldGrow` both route through it. `Snake::Destroy` now
calls `entityManager.RemoveEntity` per segment before clearing `body`.

`GameplayScene` now owns both `entityManager` (`std::unique_ptr<Core::Entities::IEntityManager>`,
constructed against the concrete `Engine::Entities::EntityManager` only inside the `.cpp`) and
`snake` (`std::unique_ptr<Snake>`), declared in that order — `entityManager` before `snake` —
so destruction tears down the observer (`snake`) before the owner (`entityManager`), matching
the design doc's §6 destruction-order caveat.

Two design questions were resolved along the way:

- **Transform pointer lifetime**: confirmed `AppleParams`/`SnakeSegmentParams`' raw
  `ITransform2D*` is safe to point at a stack-local `Transform2D`, because
  `TransformComponent2D`'s pointer constructor (`transform-component-2d.cpp:26-32`) copies the
  pointee's `position`/`rotation`/`scale` synchronously during `Entity`'s own constructor
  (`entity.cpp:19-22`) — the pointer never needs to outlive the call. This closes out F3 from
  the design doc; no dangling reference exists there.
- **`EntityManager` via DI, rejected**: considered resolving `EntityManager` through the DI
  container and passing it into `GameplayScene` via `GameplaySceneParams`, but
  `DependencyInjector::ResolveImplementation` (`dependency-injector.cpp:43-44`) caches every
  resolved instance on first use — even a nominally-transient `Register<>()` registration
  becomes a de-facto app-lifetime singleton after its first `Resolve`. Since `GameplayScene`
  itself is `SceneLifetime::Transient` and gets rebuilt on every `SwitchTo`, a DI-resolved
  `EntityManager` would leak entities across every scene re-entry instead of getting torn down
  with the scene. `GameplayScene` constructing its own `EntityManager`, as it already does,
  ties entity lifetime to scene lifetime for free.

### Stage 3 — Register/Unregister Discipline (design doc §4.4/§4.5)

Found that nothing in the codebase ever called `RenderComponent2DManager::Unregister` —
entities were destroyed via `EntityManager::RemoveEntity`, but their render components stayed
registered as dangling raw pointers inside `RenderComponent2DManager`. Designed and implemented
a general component-registrar architecture to close this, rather than a one-off fix:

- `Core::Entities::IComponentRegistrar` (new) — type-erased `Register(IComponent*)` /
  `Unregister(IComponent*)`.
- `Engine::Entities::TypedComponentRegistrar<TComponent>` (new) — template base doing the one
  shared `dynamic_cast`, exposing protected `OnRegistered`/`OnUnregistered` typed hooks. Named
  to match the existing `OnActivate`/`OnRegistration` lifecycle-hook convention already used on
  `Entity` (`entity.hpp:46-47`) — `RegisterTyped`/`UnregisterTyped` was rejected as clunky,
  `Setup`/`Teardown` was rejected as confusable with the same-named but differently-scoped
  `Teardown(IEntity*)` one layer up.
- `Engine::Entities::Registrars::RenderComponentRegistrar` (new,
  `engine/entities/registrars/`) — first concrete registrar, wraps `RenderComponent2DManager`.
- `ComponentDispatcher` changed from a `type_index`-keyed handler map to a flat
  `std::vector<std::unique_ptr<IComponentRegistrar>>` plus `AddRegistrar`/`Teardown`.
  `Dispatch`/`Teardown` iterate every registrar against every component — safe, since each
  registrar self-filters via its own `dynamic_cast`.
- `IComponentDispatcher` and `IEntityComponentPipeline` both gained a `Teardown(IEntity*)`
  pure virtual mirroring `Dispatch`/`Run`.
- `EntityManager::RemoveEntity` now calls `componentPipeline.Teardown(entity)` before erasing
  the entity — the actual linchpin: observer notified before the owner frees the object.

Two alternative designs were considered and rejected before landing here — see Architectural
Decisions.

A handful of implementation slips were caught (mostly by the user, live, mid-session) before
the final build went clean: `TypedComponentRegistrar::Unregister` initially called the wrong
hook (a stale `RegisterTyped` name left over from before the `OnRegistered`/`OnUnregistered`
rename); a `std::make_unique<T>(...)` call in `EntityComponentPipeline`'s constructor had a
dropped `<`; `ComponentDispatcher::AddRegistrar` was declared but never defined; and the new
`render-component-registrar.cpp` was missing from `CMakeLists.txt`'s explicit source list
(this build has no glob, so new `.cpp` files are silently never compiled until added by hand).
All fixed; full rebuild clean. Committed as `aa84fa3`.

### AddressSanitizer Run + Crash Diagnosis

Per the design doc's final migration step, configured a second build directory
(`build-asan/`), passing sanitizer flags via `-DCMAKE_CXX_FLAGS`/`-DCMAKE_EXE_LINKER_FLAGS` at
the CMake configure step rather than editing `CMakeLists.txt`. Ran the game and hit an
immediate `SEGV` on startup — unrelated to the ownership migration just completed.

Root cause: `GameContext::input` (`gameplay-state-machine.hpp:22`, a
`std::unique_ptr<InputSystem>`) is default-null and never assigned anywhere in the codebase
(one commented-out assignment attempt exists at `game-over-state.cpp:17`).
`GameplayStateMachine`'s constructor starts in `MainMenuState`, whose `Update`
(`main-menu-state.cpp:23`) dereferences the null `input` pointer, segfaulting inside
`InputSystem::IsActionPressed` (`input-system.cpp:20`) reading `this->keyMap[...]` on a null
`this`. Confirmed this predates this session's work entirely — input-system wiring is
already-tracked upcoming work (UE-0017) — not a regression from the ownership migration.

Tracing the crash surfaced two further landmines on the same dead code path, neither
previously tracked:

- `GameplayState::snake`/`GameplayState::apple` (`gameplay-state.hpp:34-35`) are separate,
  always-null members, distinct from `GameplayScene::snake`/`apple` — nothing anywhere ever
  assigns them. `GameplayState::Enter()` (`gameplay-state.cpp:28-36`) would hit its own
  `LOG_FATAL`+`assert` immediately if it ever ran, independent of the input problem.
- `Snake::Update(float deltaTime)` (`snake.cpp:41`) — which drives movement, growth
  (`CheckIfShouldGrow`), and boundary wrap (`Teleport`) — is never called from anywhere in the
  codebase. It was presumably meant to be driven from `GameplayState::Update`, but that path is
  dead per the point above. So even with the scene/entity update loop running, the snake
  cannot move today regardless of input state.

Applied a minimal, deliberate workaround — not a fix — to unblock further work: commented out
the one line in `GameplayStateMachine`'s constructor (`gameplay-state-machine.cpp:16`) that
changes state to `MainMenuState`, leaving `currentState` null.
`Engine::State::StateMachine::Update` (`state-machine.cpp:27-33`) already null-checks and
no-ops in that case, so `GameplayScene::Update`'s call to `stateMachine.Update(...)` becomes a
no-op while `entityManager->OnUpdate(...)` keeps running normally. The game now boots and
renders the initial snake/apple without crashing. Movement and input stay inert until UE-0017
and the `GameplayState` snake/apple wiring land — see UE-0035 below.

While tracing this, also confirmed `GameplayStateMachine` **no longer holds an `entityManager`
member at all** — grepped, no matches in `gameplay-state-machine.hpp`/`.cpp`. This wasn't
touched in today's diff (`git show --stat aa84fa3` shows those files untouched this session),
so it must have been resolved in an earlier session, and this session just verified it. Closes
out the "duplicate `EntityManager`" concern (design doc F9) carried forward from the previous
log.

## Lessons Learned

### A Cache-on-First-Resolve DI Container Has No "Transient" Below the Container's Own Lifetime

`DependencyInjector::ResolveImplementation` caches whatever a factory produces into an
`instances` map the first time it's resolved (`dependency-injector.cpp:43-44`), and every
subsequent `Resolve<T>()` returns that same cached instance — regardless of whether `T` was
registered via `Register<>()` ("transient") or `RegisterSingleton<>()`. There is no actual
per-call transient resolution in this container; "transient" only describes how the value is
*produced* the first time, not how often. This matters any time an object's lifetime needs to
be shorter than the whole application's — routing it through the container doesn't give you
that, no matter which `Register*` variant you pick.

### A Component's `dynamic_cast` Can Live in One Shared Place

Considered two designs for wiring per-component-type registration behaviour (register a
render component with its manager, etc.) before landing on the current one:
`TypedComponentRegistrar<T>`, a small template base class that performs `dynamic_cast<T*>`
once and exposes already-typed `OnRegistered`/`OnUnregistered` hooks to its subclasses. Every
future component kind (collider, audio) gets a named, independently-testable, discoverable
class instead of an anonymous lambda buried in a pipeline constructor, and the cast logic
exists exactly once regardless of how many component kinds show up later.

### RAII-Style Closures Aren't Always the Right Answer

Before landing on the registrar-class design, considered having a registration callback
*return* its own teardown as a captured closure (`std::function<void()>`), so register/
unregister behaviour could never drift apart because they're written as one function body.
Discarded once it became clear `Unregister` in this codebase needs no state beyond the manager
and the component pointer — both trivially available again at teardown time — so the closure
approach would have added a whole liveness-tracking map (component pointer → pending teardown
closure) to solve a problem that didn't actually exist here. Worth remembering generally: RAII/
closure-capture patterns pay for themselves when teardown genuinely needs data from the setup
call; when it doesn't, they're bookkeeping for nothing.

## Architectural Decisions

### Component Registration: Registrar Classes, Not a Second Dispatcher or Self-Cleaning Closures

Landed on `IComponentRegistrar` + `TypedComponentRegistrar<T>` (see Work Completed) after
rejecting two alternatives in sequence:

1. **A second, parallel `ComponentDispatcher` instance** (one for register, one for unregister)
   — rejected as a "bandage fix": it duplicates the type-map/`dynamic_cast` machinery for what
   is really one lifecycle concept, and splits the register/unregister pairing for a given
   component type across two independently-maintained call sites, where it's easy to add one
   half and forget the other.
2. **Closures returned from a `RegisterHandler` callback**, each closure capturing its own
   teardown — rejected once it was clear `Unregister` needs no per-call captured state here
   (see Lessons Learned above); the closure map would have been bookkeeping for a problem that
   doesn't exist in this codebase's actual `Register`/`Unregister` shape.
3. **Landed on**: polymorphic `IComponentRegistrar` subclasses, one per component kind, holding
   their manager dependency as an ordinary member. `Register`/`Unregister` are two methods on
   the same long-lived object — nothing to capture, nothing to go stale.

### Registrars Live in `engine/entities/registrars/`, Not Per-Module

Considered splitting concrete registrars across the modules they touch (`RenderComponentRegistrar`
under `renderer-2d/`, a future `AudioComponentRegistrar` under `audio/`, etc.), but decided to
colocate them all under `engine/entities/registrars/` instead — where their sole consumer,
`EntityComponentPipeline`, already lives. Rationale: a registrar's `Register(IComponent*)`
signature only makes sense in the context of the generic, type-erased entity/component dispatch
system doing the casting; if `renderer-2d` or `audio` ever needed to register something with
their own manager *outside* the entity system, they'd just call the manager directly with an
already-typed pointer — they'd have no reason to go through an `IComponentRegistrar` at all.
Matches the existing precedent of `EntityComponentPipeline` itself, which already references
`Core::Rendering::IRenderComponentManager` by interface while living in `engine/entities`.

### `EntityManager` Stays Constructed by `GameplayScene`, Not DI-Resolved

See Lessons Learned — the DI container's cache-on-first-resolve behaviour makes it unsuitable
for anything that needs to be scoped shorter than the whole application. Recorded here as a
standing constraint for future sessions: don't route session/scene-scoped objects through
`DependencyInjector` without first giving the container a real per-call-transient mechanism,
which it does not have today.

### ASan Wired in via a Second Build Directory, Not a `CMakeLists.txt` Edit

Verification per the design doc's final migration step needed an ASan build, but
`CMakeLists.txt` is off-limits for the agent to edit under this repo's read-only policy.
Configured a parallel `build-asan/` directory instead, passing
`-DCMAKE_CXX_FLAGS="-fsanitize=address ..."` and `-DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address"`
at the CMake configure step — a build invocation, not a source or build-file edit — keeping the
policy intact while still getting a real, instrumented run.
